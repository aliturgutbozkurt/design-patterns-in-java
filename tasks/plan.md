# Implementation Plan: Design Patterns in Java (Java 27, Fall 2026)

> Source spec: [`SPEC.md`](../SPEC.md) · Task list: [`tasks/todo.md`](todo.md) · Each task ↔ one GitHub issue
> (milestone = phase/module, labels `type:*` + `module:*`). Status: **APPROVED** (2026-09-25).

## Overview

Build the course in four phases: **Foundation** (build, tests, docs/PDF pipeline, CI) → **Modules m00–m11**
(each: spec → examples → lesson EN/TR/PDF → assignments) → **Capstone** → **Release**.
Module m00 doubles as the *pilot* that proves the whole per-module template end-to-end before the other 11 modules are produced.

## Architecture decisions

| # | Decision | Rationale |
|---|---|---|
| AD1 | Maven multi-module, one Maven module per course module, parent POM pins versions | Students can build one module in isolation; one place to bump JDK/deps |
| AD2 | `src/main` has no third-party dependencies | Every demo runs with `java File.java` (multi-file source launcher, JEP 458) — "easy to run" requirement |
| AD3 | Exercises and solutions in the same Maven module, different packages, bound to one **abstract contract test** | Student code and reference solution are held to identical tests; CI proves solutions pass |
| AD4 | `@Tag("exercise")` tests excluded by default; `-Pexercises` runs them; `scripts/check-starters.sh` proves starters compile and still fail (F03 refinement: starters live in `src/main`, so the default build already compiles them) | Default build is green while starters are intentionally incomplete |
| AD5 | Lessons authored in Markdown + Mermaid, PDFs generated by pandoc → Typst with Mermaid pre-rendered via `mermaid-cli` | GitHub renders Markdown natively; Typst gives good Turkish typography without a TeX install |
| AD6 | EN is authored first, TR follows with identical structure; `check-docs.sh` enforces heading parity | Keeps the two languages from drifting |
| AD7 | Lesson code blocks are extracted from compiled source files (reference path under each block) | Code shown to students always compiles and is tested |
| AD8 | Prefer final Java features; preview features only if `docs/java27-features.md` lists them and the module spec opts in | Course material must not break on the next JDK |
| AD9 | Each module gets its own `specs/SPEC-<id>.md` written *just in time* (first task of the module) and human-approved | SDD gate per module without writing 12 specs up front that would go stale |

## Dependency graph

```
F01 build skeleton ─┬─ F02 Java 27 feature audit
                    ├─ F03 test harness (tags, profiles, contract pattern)
                    ├─ F04 docs & PDF pipeline ── F05 CI ── F06 community files/README
                    └──────────────────────────────┐
                                                   ▼
        M00 (pilot) → M01 → M02 → … → M11 → Capstone (C1…C7) → Release (R1, R2)
        within each module:  spec(-1) → examples(-2a/-2b) → lesson(-3) ┐
                                                  └──────→ assignments(-4)┘
```

Within a module, lesson (-3) and assignments (-4) both depend on examples (-2) and can proceed **in parallel**.
Across modules, work is sequential for teaching coherence, but a module's spec (-1) may be drafted while the
previous module's lesson is being translated.

## Content blueprint per module

- **Spec (-1):** learning outcomes (Bloom verbs), prerequisites, pattern list, ≥ 2 examples per pattern (names + domain),
  assignment briefs with acceptance criteria, quiz topics, Java 27 features used.
- **Examples (-2):** per pattern: minimal canonical example + realistic domain example (+ modern variant); each has a `main`
  with deterministic output and a JUnit test.
- **Lesson (-3):** `lesson.en.md` → `lesson.tr.md` → PDFs → module `README.md`. Template in `docs/templates/lesson.md`.
- **Assignments (-4):** ≥ 2 assignments; EN + TR brief, starter (`exercises/exNN`), contract test, `*ExerciseTest`, solution, `*SolutionTest`.

Task-size note: for content tasks, "files touched" counts one example package / one lesson / one assignment as a unit;
modules with 4+ patterns split their examples task in two (-2a / -2b) to stay at S/M size.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Tooling (JaCoCo, ArchUnit, Maven plugins) not yet supporting class file 71 (JDK 27) | High | F01 spikes each tool first; drop or pin to supported versions; record in `docs/java27-features.md` |
| Assumed Java features are still preview in 27 (e.g. structured concurrency) | Med | F02 audits JEP status from openjdk.org before any module spec relies on it; preview code isolated behind a profile |
| Local Maven runs on JDK 23 (seen on author's machine) | Med | `.mvn/jvm.config` / docs require `JAVA_HOME` 27; enforcer plugin `requireJavaVersion [27,)` |
| EN/TR drift | Med | Parity check script in CI; TR task follows EN in the same PR |
| PDF toolchain (pandoc + typst + mermaid-cli) differs across machines | Med | Pin versions; build PDFs in CI; commit generated PDFs |
| Flaky concurrency tests (m10) | Med | Deterministic designs (latches, injected executors/clocks); no `sleep`-based assertions |
| Scope size (12 modules × 4 tasks + capstone) | High | Pilot first; strict DoD; per-module specs keep scope bounded; parallelize lesson/assignments |
| Copyright (GoF / textbook examples) | Med | Original examples and wording; cite sources in "Further reading" only |

## Parallelization

- Safe: lesson (-3) ∥ assignments (-4) within a module; TR translation ∥ next module's spec; PDF regeneration.
- Sequential: Foundation tasks F01 → F03/F04 → F05; capstone reference slices C3 → C6.
- Needs coordination: changes to the lesson template or contract-test pattern (affects all modules → update pilot first).
